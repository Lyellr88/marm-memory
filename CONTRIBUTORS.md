The PR introduced a separate STDIO entrypoint, transport-specific requirements, shared-core tool wiring, response-size handling, and setup documentation while keeping the existing HTTP path intact ([#20](https://github.com/Lyellr88/marm-memory/pull/20)).
- **sarvesh1327** ([@sarvesh1327](https://github.com/sarvesh1327)) — Fixed runtime preset handling so an explicit `COMPACTION_TRIGGER_COUNT` environment override is preserved instead of being clobbered by default/swarm/trusted presets. Added regression coverage for operator/Docker tuning paths around compaction trigger configuration ([#43](https://github.com/Lyellr88/marm-memory/pull/43)).
- **zza-830** ([@zza-830](https://github.com/zza-830)) — Hardened configuration parsing with bounds checks and clamping warnings across server ports, rate limits, queue sizes, recall limits, compaction settings, and search weights. Also added `MARM_RECALL_DEBUG` observability so recall lane selection, fallback behavior, and candidate breakdowns can be inspected safely through stderr without adding new MCP tools ([#54](https://github.com/Lyellr88/marm-memory/pull/54)).
- **Vaishnavi Desai** ([@vaishnavidesai09](https://github.com/vaishnavidesai09)) — Added the exact retrieval lane for code, config, command, and API-contract queries. The work introduced syntax-heavy query detection, the `exact_mode` control surface, deterministic FTS/BM25 recall with LIKE fallback, full HTTP/STDIO/service/core parameter wiring, project/platform scoping in exact recall, and regression coverage for routing, ranking, fallback behavior, and response compatibility ([#71](https://github.com/Lyellr88/marm-memory/pull/71)).
- **Muneeb Ahmad** ([@Mxneeb](https://github.com/Mxneeb)) — Proposed replacing min-max fusion with Reciprocal Rank Fusion on the hybrid recall path, with a complete implementation and a documented mathematical rationale ([#112](https://github.com/Lyellr88/marm-memory/pull/112)). The change was not merged, but the implementation became the reference for a controlled bake-off: a weighted RRF variant preserving MARM's shipped lexical weight, so fusion was the only variable. RRF measured 6.8-7.3pp below min-max across all five LoCoMo categories, which settled a question that had been open on reasoning alone and produced the fusion decision record in `docs/current/`. The experiment also corrected MARM's estimate of its own benchmark noise from ~0.1pp to 0.56pp, a methodology fix that outlives the experiment. Separately reported a real consolidation defect, fixed in v2.42.0 ([#113](https://github.com/Lyellr88/marm-memory/issues/113)): `CONSOLIDATION_THRESHOLD` is documented as a cosine threshold but was compared against a blended ranking score, which proved to be live under min-max as well, not introduced by the RRF proposal. Also surfaced the chunk-count bias in `_score_chunk_aware`'s max-over-chunks pooling, since measured and confirmed, and independently identified the recall risk the FTS candidate filter carries for low-token-overlap paraphrases.
- **erfou11** ([@erfou11](https://github.com/erfou11)) - Gave MARM's first endpoints a real response schema. `marm_log_entry` and `marm_delete` moved from a bare `dict` to declared Pydantic response models, so the OpenAPI document now describes their payloads instead of an untyped object, and a renamed response field is caught by the schema rather than shipping silently ([#175](https://github.com/Lyellr88/marm-memory/pull/175)). The models set `extra="forbid"`, which turns FastAPI's default behavior of quietly dropping undeclared fields into a loud failure, and the tests pin the client-facing HTTP 500 that produces. Payload parity was proven in both directions: every success, session-switch, not-found and error shape preserved, and the 14 MCP tool descriptions and input schemas verified unchanged, which was the main risk in attaching a response model to a tool surface ([#167](https://github.com/Lyellr88/marm-memory/issues/167)).
- **Quang** ([@quangshuynh](https://github.com/quangshuynh)) - Reconciled the two code paths that write `~/.marm/.env`, which disagreed on what to do when file permission hardening fails ([#166](https://github.com/Lyellr88/marm-memory/issues/166)). Server startup previously swallowed a `chmod` failure with a bare `except OSError: pass` and continued with a readable plaintext bearer token on disk, while the CLI path treated the same failure as fatal. Startup now reuses the existing `_protect_key_file` helper rather than keeping a second copy of the hardening logic, removes the file when protection cannot be verified, and continues with the generated key in memory only, so a `chmod` or Windows ACL failure leaves nothing readable behind and still never blocks startup on `0.0.0.0`. `services/key_management.py` was deliberately left fail-loud, preserving the intended asymmetry between interactive setup and unattended startup. A follow-up commit extended the same fallback to non-`OSError` failures, which is the case that matters on Windows where the ACL work is `ctypes` and can raise past an `OSError` catch. Tests cover successful protection, protection returning false, protection raising, and removal itself failing, and the success-path test exercises the real protector and asserts owner-only permissions on POSIX instead of stubbing it ([#173](https://github.com/Lyellr88/marm-memory/pull/173)).
- **Anton Dziatkovskii** ([@tonydzi](https://github.com/tonydzi)) - Repaired `scripts/test-scripts/smoke_embedding_chunking.py` against the v2.14.0 chunk-profile split, closing the harder of the two remaining scripts named in the wider alignment audit ([#165](https://github.com/Lyellr88/marm-memory/issues/165)). It was not a rename: the script imported `CHUNK_THRESHOLD_WORDS`/`CHUNK_TOKEN_LIMIT`/`CHUNK_OVERLAP_TOKENS`, which the split replaced with separate `MEMORY_*` and `DOC_*` profiles, and the fixture body was 343 words against the current 500-word memory threshold (180 before v2.14.0), so `_chunk_text` returned nothing and every chunking assertion would have passed vacuously rather than for real. The fixture now clears the threshold, and the two assertions describing the old fixed sliding window were rewritten to the current even-split-plus-padding shape, verified line by line against `_chunk_text`/`_split_evenly` and confirmed to fail under three independent mutations (wrong profile, reverted fixture, zeroed overlap). Also read the other six scripts against the current `core/` layout and reported two contracts that have moved but were left out of scope: three HTTP smoke harnesses still POST to `/marm_context_log`, a route removed two months ago, and `smoke_hybrid_search.py` registers exactly one real assertion despite printing results for four queries ([#181](https://github.com/Lyellr88/marm-memory/pull/181)).

## Test & Documentation Contributors

- **Aditya** ([@adity982](https://github.com/adity982)) — Made the zero-temporal-weight regression test verify what it claimed. The old assertion only compared the two candidates' positions when the second one happened to surface, so it could pass without ever exercising the ordering relationship it described. The test now stubs the lexical lane to return both candidates with fixed scores, pins `HYBRID_SEARCH_TEXT_WEIGHT`, and asserts the exact result order ([#124](https://github.com/Lyellr88/marm-memory/pull/124)). Documentation only.
- **mikemikimike** ([@mikemikimike](https://github.com/mikemikimike)) - Repaired the import block in `scripts/test-scripts/smoke_hybrid_search.py`, which still pulled `_fetch_and_score_embedding_rows` and `_fetch_and_score_fts_rows` from `core.memory` after both had moved to `core.memory_scoring`. The script raised `ImportError` before reaching any assertion, so it could not run at all ([#171](https://github.com/Lyellr88/marm-memory/pull/171)). Covers one of the scripts named in the wider alignment audit ([#165](https://github.com/Lyellr88/marm-memory/issues/165)).
- **Nikhil Shirke** ([@NIKHILSHIRKE56](https://github.com/NIKHILSHIRKE56)) - Fixed the `marm-init` setup verification so it stops claiming more than it proved. Docker HTTP always requires a key, but the final check hit the public `/health` route, which passes identically whether the key is right, wrong, or absent, so the one thing most likely to be broken was the one thing the check could not detect ([#172](https://github.com/Lyellr88/marm-memory/issues/172)). Keyed paths now assert a 401 on a protected route to prove auth is armed, then hand the authenticated check to the user in their own terminal, so the credential still never enters the setup conversation. Keyless loopback servers keep the `/health` check, which is required rather than cosmetic: with no key configured the auth middleware admits localhost, so a 401 assertion there would fail a correct setup ([#176](https://github.com/Lyellr88/marm-memory/pull/176)).
- **Anton Dziatkovskii** ([@tonydzi](https://github.com/tonydzi)) - Repaired the 17 dead links in `marm-mcp-server/README.md`, the file `pyproject.toml` declares as `readme` and therefore the description PyPI renders. All 17 were written relative to the repository root, a position neither surface that renders this file ever occupies: on PyPI they resolved against the project page, and on GitHub they resolved next to the file under `marm-mcp-server/`. Both 404, including the install and key-setup pointers a first-time `pip install` reader is most likely to click. Verified against the live published description rather than the working tree, then rewritten to absolute URLs on `MARM-main`, the same form the file's own Project Documentation section already used, with link text untouched. Also diagnosed why `scripts/scan-stale-docs.py` reported clean: `resolve_ref` accepts a link that exists from the repository root regardless of where the linking document sits. The scanner was deliberately left alone rather than tightening a shared gate, since the same logic also guards the packaged `resources/marm-docs/` copies and whether those should carry absolute links is a maintainer decision ([#180](https://github.com/Lyellr88/marm-memory/pull/180)).
