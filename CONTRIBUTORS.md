- **Muneeb Ahmad** ([@Mxneeb](https://github.com/Mxneeb)) — Proposed replacing min-max fusion with Reciprocal Rank Fusion on the hybrid recall path, with a complete implementation and a documented mathematical rationale ([#112](https://github.com/Lyellr88/marm-memory/pull/112)). The change was not merged, but the implementation became the reference for a controlled bake-off: a weighted RRF variant preserving MARM's shipped lexical weight, so fusion was the only variable. RRF measured 6.8-7.3pp below min-max across all five LoCoMo categories, which settled a question that had been open on reasoning alone and produced the fusion decision record in `docs/current/`. The experiment also corrected MARM's estimate of its own benchmark noise from ~0.1pp to 0.56pp, a methodology fix that outlives the experiment. Separately reported a real consolidation defect, fixed in v2.42.0 ([#113](https://github.com/Lyellr88/marm-memory/issues/113)): `CONSOLIDATION_THRESHOLD` is documented as a cosine threshold but was compared against a blended ranking score, which proved to be live under min-max as well, not introduced by the RRF proposal. Also surfaced the chunk-count bias in `_score_chunk_aware`'s max-over-chunks pooling, since measured and confirmed, and independently identified the recall risk the FTS candidate filter carries for low-token-overlap paraphrases.

- **Quang** ([@quangshuynh](https://github.com/quangshuynh)) - Reconciled the two code paths that write `~/.marm/.env`, which disagreed on what to do when file permission hardening fails ([#166](https://github.com/Lyellr88/marm-memory/issues/166)). Server startup previously swallowed a `chmod` failure with a bare `except OSError: pass` and continued with a readable plaintext bearer token on disk, while the CLI path treated the same failure as fatal. Startup now reuses the existing `_protect_key_file` helper rather than keeping a second copy of the hardening logic, removes the file when protection cannot be verified, and continues with the generated key in memory only, so a `chmod` or Windows ACL failure leaves nothing readable behind and still never blocks startup on `0.0.0.0`. `services/key_management.py` was deliberately left fail-loud, preserving the intended asymmetry between interactive setup and unattended startup. A follow-up commit extended the same fallback to non-`OSError` failures, which is the case that matters on Windows where the ACL work is `ctypes` and can raise past an `OSError` catch. Tests cover successful protection, protection returning false, protection raising, and removal itself failing, and the success-path test exercises the real protector and asserts owner-only permissions on POSIX instead of stubbing it ([#173](https://github.com/Lyellr88/marm-memory/pull/173)).

- **mikemikimike** ([@mikemikimike](https://github.com/mikemikimike)) - Repaired the import block in `scripts/test-scripts/smoke_hybrid_search.py`, which still pulled `_fetch_and_score_embedding_rows` and `_fetch_and_score_fts_rows` from `core.memory` after both had moved to `core.memory_scoring`. - **Nikhil Shirke** ([@NIKHILSHIRKE56](https://github.com/NIKHILSHIRKE56)) - Fixed the `marm-init` setup verification so it stops claiming more than it proved. Docker HTTP always requires a key, but the final check hit the public `/health` route, which passes identically whether the key is right, wrong, or absent, so the one thing most likely to be broken was the one thing the check could not detect ([#172](https://github.com/Lyellr88/marm-memory/issues/172)). Keyed paths now assert a 401 on a protected route to prove auth is armed, then hand the authenticated check to the user in their own terminal, so the credential still never enters the setup conversation. Keyless loopback servers keep the `/health` check, which is required rather than cosmetic: with no key configured the auth middleware admits localhost, so a 401 assertion there would fail a correct setup ([#176](https://github.com/Lyellr88/marm-memory/pull/176)).
